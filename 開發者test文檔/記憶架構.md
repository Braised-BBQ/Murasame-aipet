# 記憶架構與機制說明

## 一、雙層雙模大腦與自述錨點架構
系統的記憶底層由兩個資料庫、一個文本錨點機制與雙模態架構組成：
* **雙腦模型分工 (成本最佳化)：** 前台陪伴採用高擬真主模型負責情感共鳴與對話；後台記憶處理引擎則切換為輕量級模型（如 Gemini 1.5 Flash-8b），專注執行標籤萃取與 JSON 結構化輸出，大幅降低 API 預算消耗，同時維持高容錯率。
* **拓樸層 (ChromaDB)：** 專注儲存記憶的語義特徵與事件標籤。每一筆寫入的 metadata 包含：建立時間、SQLite 對應 ID、S_base 分數、標籤數量、是否為未解決事件 (`is_unresolved`)、喚醒次數 (`recall_count`)、因果關聯 ID (`parent_id`) 以及記憶類型 (`type`)。
* **全資訊層 (SQLite)：** 負責記錄每一句對話的角色 (`role`)、原始內容與精確時間戳記 (`timestamp`)，用以還原完整上下文。為避免資料無限膨脹，記憶陣列最大保留歷史輪數為設定值的 2 倍。
* **雙軌自述錨點 (Anchor)：** 大腦在生成回覆前，會動態讀取文本檔案注入系統提示詞中。系統會讀取永久核心錨點 (`core_anchor.txt`) 的最後 5 筆作為靈魂核心記憶，並讀取近期情緒錨點 (`recent_anchor.txt`) 的最後 3 筆作為當前的內心狀態。

## 二、記憶寫入、S_base 分級與拓樸精度提升
在提取記憶寫入資料庫時，系統會呼叫 LLM 進行綜合評估，並透過嚴格的提示詞規範提升向量庫的純淨度：
* **前置因果關聯掃描：** 在呼叫 LLM 評估前，系統會先以使用者的輸入向 ChromaDB 查詢，若找到語意距離 < 1.2 的舊記憶，會將該 ID 作為 `potential_parent_id` 提供給 LLM 判斷因果關聯。
* **S_base 分級與標籤數量控制：**
  * **[0-29] 忽略區間：** 無意義語氣詞，不寫入長期記憶。
  * **[30-49] 日常短期記憶：** 最多提取 2 個關鍵標籤。
  * **[50-79] 中期重要記憶：** 允許提取 3 至 5 個標籤。
  * **[80-94] 長期深刻記憶：** 允許提取 6 至 10 個標籤，並由 LLM 撰寫第一人稱內心獨白，寫入近期情緒錨點。
  * **[95-100] 永久核心記憶：** 允許提取最多 15 個標籤，撰寫內心獨白寫入永久核心錨點。
* **拓樸精度約束與字數暴政：** 放棄死板的固定標籤字典，改用「維度化打標 (實體、動作、情感)」，藉此極大化向量空間的共鳴能力。提示詞同時導入「字數暴政 (每個標籤限 2~5 字)」與正反範例 (Few-Shot)，嚴格禁止保留口語字綴或完整短句，確保特徵純粹。
* **特殊標記與時間錨點化：** 若涉及使用者個人資料，強制加入 `[主人情報]` 標籤以收束事實類問題的檢索發散。若 S_base >= 80，強制加入如 `[核心約定]` 或 `[情感羈絆]` 等金標。若提及未來計畫或過去時期，必須將時間轉化為獨立標籤。
* **事實濃縮 (Fact Condensation)：** 若 LLM 判斷對話具備記憶價值 (`has_event: true`)，必須將內容濃縮成一句客觀、精煉的事實句存入 `fact` 欄位。

## 三、非對稱檢索與綜合權重評估
記憶的喚醒依賴前置轉譯與多維度數學權重計算：
* **LLM 前置意圖與時間雙效萃取：** 大腦在發起檢索前，會先呼叫輕量 LLM 從使用者輸入中萃取核心標籤，並直接推算出目標時間 (`target_days_ago`) 與模糊寬容度 (`time_window`)。提示詞中特別加入防呆機制，教導 LLM 嚴格區分「事件發生的未來時間」與「過去對話的時間」，避免時間指代錯亂導致的高斯加權失效。
* **擴大本地召回池 (突破時間盲點)：** 為解決 ChromaDB 第一階段純依賴語義、無視時間衰減的「海選瓶頸」，系統將初步抓取的 `n_results` 放寬至 15 筆，讓更多隱藏的高價值記憶有機會進入 Python 引擎進行第二階段精確計分。
* **喚醒權重公式 ($W_m$) 與門檻自適應：** 系統計算 ChromaDB 回傳的候選記憶，得分最高且 $W_m \ge 0.38$ (適度放寬門檻以防純事實記憶遭誤殺) 才會成功喚醒。公式為：
  $$W_m = \left( \left( 0.7 \times \text{sim}^2 + 0.3 \times \frac{N_{\text{tags}}}{10} \right) \times v_t \times p_c \right) + t_{\text{bonus}}$$
  * **sim (銳化相似度)：** 基礎相似度 $\frac{1}{1 + \text{distance}}$ 的平方，用於拉大高低相關記憶的差距。
  * **$N_{\text{tags}}$ (資訊豐富度)：** 該筆記憶的標籤總數（上限 10）。
  * **$p_c$ (防疲勞冷卻)：** 4 小時內曾喚醒為 0.1，24 小時內為 0.5，否則為 1.0。
  * **$v_t$ (動態時間衰減)：** 若 S_base >= 95 則強制為 1.0。其餘為 $e^{-effective_{decay} \times \Delta\text{days}}$。其中 $effective_{decay} = \max(0.001, base_{decay} \times 0.8^{recall_{count}})$，`base_decay` 依據 S_base >= 80 決定為 0.005 或 0.05。
  * **$t_{\text{bonus}}$ (高斯時間加權)：** 基於目標日與記憶發生日的天數落差，公式為 $0.3 \times e^{-\frac{diff_{days}^2}{2 \times window_{days}^2}}$。
* **記憶鞏固與因果鏈溯源 (具備 DAG 環狀防護)：** 記憶被成功喚醒後，該筆記憶的 `recall_count` 會加 1。系統接著會根據 `parent_id` 向上追溯最多 3 層的因果關聯記憶，並透過集合紀錄已走過的節點，若偵測到循環鎖死 (A->B->A) 則強制切斷防護。
* **動態時間窗切片：** 提取成功後，系統根據 SQLite ID 抓取上下各 6 句對話，嚴格限制對話必須發生在目標時間點的「前後 15 分鐘以內」。若時間戳找不到，退回抓取上下 2 句。

## 四、記憶代謝、排程防護與狀態轉換
系統具備自動清理與狀態轉換機制以維持運行效率，專為「用完即關機」的桌面情境設計：
* **消除向量污染的記憶代謝：** 系統開機 5 分鐘後會啟動背景排程執行代謝。若記憶的 S_base < 80 且 `recall_count` < 3，當算出的衰減係數 $v_t < 0.01$ 時，系統會自動從向量庫物理刪除該筆記憶。此舉能釋放寶貴的召回名額，防止低分殭屍記憶引發的「向量空間污染」。
* **全資訊層延遲清理：** 開機 10 分鐘後會觸發 `run_half_year_cleanup` 進行例行 SQLite 資料庫清理，完美避開開機尖峰，取代容易錯失的固定日期排程。
* **因果鏈防重複排程 (回音室阻斷)：** 若寫入的記憶為未來排程 (`is_future_reminder: True` 且帶有時間)，系統會查詢 ChromaDB 中相同時間點且類型為 `reminder` 的記憶。若存在且語意距離 < 0.4，系統將直接攔截，不再建立新記憶，徹底解決因果鏈喚醒造成的無限重複排程災難。提示詞也加上致命規則，禁止將「對舊排程的回顧」標記為新排程。
* **主動關懷與狀態轉換：** 隨機搭話事件觸發時，系統會查詢帶有 `is_unresolved: True` 標記的記憶。若有，系統會在提示詞中強制要求模型主動關心該事件，並將該記憶的 `is_unresolved` 更新為 `False`。
* **排程降級機制：** 當排定的時間到達並觸發提醒後，系統會將該筆記憶在 ChromaDB 中的 `type` 從 `reminder` 降級為 `fact`，防止重啟軟體時再次觸發。系統重載時，若發現昨天以前的過期提醒，也會直接將其降級為 `fact` 並取消排程。
